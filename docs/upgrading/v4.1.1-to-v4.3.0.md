# 4.1.1 to 4.3.0

This page covers **v4.2.0** (2026-10-11) and **v4.3.0** (not yet cut when this page was written; it is the release after v4.2.0). Pin `?ref=v4.3.0` to take both steps at once. Both releases are additive: a consumer that sets no new input plans **no changes** against v4.1.1 state, apart from the new plan-time outputs listed under v4.3.0.

## Expected plan

### v4.2.0

[`CHANGELOG.md`](../../CHANGELOG.md) records one feature: "optional request-header filter on the Cloudflare allow rules." The changelog does not state a plan diff. The feature's pull request, [#104](https://github.com/agenticcodingops/azure-wordpress/pull/104), describes the inputs as off by default: `app_service.cdn_origin_header_name` defaults to `null`, which "keeps IP-only rules" (`modules/wordpress-site/variables.tf`), so a consumer that leaves it unset plans no change. Nothing is replaced or destroyed by the upgrade itself.

### v4.3.0

The v4.3.0 changelog entry is written by the release tool when the release is cut, so this page cites the pull requests instead: [#107](https://github.com/agenticcodingops/azure-wordpress/pull/107) (staging-slot opt-out), [#109](https://github.com/agenticcodingops/azure-wordpress/pull/109) (scheduled App Service backup), [#110](https://github.com/agenticcodingops/azure-wordpress/pull/110) (`storage_key_secret_enabled`) and [#111](https://github.com/agenticcodingops/azure-wordpress/pull/111) (passwordless database access). Each states that its defaults keep the behaviour of every earlier release:

- `app_service.staging_slot_enabled` defaults to `true`;
- `app_service_backup_enabled` defaults to `false`;
- `storage_key_secret_enabled` defaults to `true`;
- the four `mysql_entra_stage_*_enabled` flags default to `false`.

So a consumer that bumps the pin without opting in plans **no resource changes**. The only visible difference is four new outputs, all known at plan time: `staging_slot_enabled` (`true` on an S\* or P\* SKU, `false` otherwise), `app_service_backup_sas_rotation_rfc3339` and `app_service_backup_sas_expiry_rfc3339` (both `null` while the backup is off) and `mysql_entra_stage` (`0`). Nothing is replaced or destroyed unless you opt in; the sections below say what each opt-in destroys.

The v4.3.0 features need two providers the module already requires: `time` (the backup's rotation window) and `azurerm`. A root that pins versions inside the module's ranges needs no change.

## v4.2.0: the origin-header filter on the Cloudflare allow rules

**New, optional: `app_service.cdn_origin_header_name` and the sensitive top-level `cdn_origin_header_values`; new, optional: `app_service_ip_security_audit_logs_enabled`.** Unset, nothing changes: the Cloudflare allow rules stay IP-only, and no audit log is sent.

Cloudflare's address ranges are shared by every Cloudflare customer, so an IP-only allow rule admits traffic that passed through any zone. When `cdn_origin_header_name` is `"x_azure_fdid"` or `"x_forwarded_host"` and `cdn_origin_header_values` holds one to eight values, every Cloudflare IPv4 and IPv6 rule on the app and its staging slot also requires one of those values in that header. The health-probe, Front Door and SCM rules are unchanged. Setting the name needs `cdn_provider = "cloudflare"` and one to eight values, or the plan fails. Turning it on is an in-place update of the app's (and the slot's) IP restrictions.

The values are bearer secrets: they sit in state, in App Service configuration and in the edge rule. Configure an edge Request Header Transform Rule that overwrites the header first, then enable the filter; reverse that order to roll back. Rotate without downtime by accepting the old and new values together, switching the edge, then removing the old value. See the composition README's [Binding Cloudflare rules to your zone](../../modules/wordpress-site/README.md#binding-cloudflare-rules-to-your-zone) and the app-service module's [Cloudflare origin header filter](../../modules/app-service/README.md#cloudflare-origin-header-filter).

## v4.3.0: the staging-slot opt-out

**New, optional: `app_service.staging_slot_enabled`** (and `staging_slot_enabled` on the app-service module), default `true`. Unset, nothing changes: an S\* or P\* SKU still gets its `staging` slot, and a B\* SKU still gets none. See [Staging Deployment Slots](../../modules/wordpress-site/README.md#staging-deployment-slots).

`false` creates no slot on a SKU that supports one. On an **existing** deployment it **destroys** the staging slot and its managed identity, the slot's Key Vault access policy (`azurerm_key_vault_access_policy.staging_slot`) and every slot diagnostic setting (`azurerm_monitor_diagnostic_setting.staging_slot`). Whatever is deployed to the slot is lost, so swap it into production first if you want to keep it. A `staging_slot_diagnostic_settings` entry left in place is ignored and the plan prints a warning, as it already does on a B\* SKU. A CanNotDelete lock blocks these deletes; remove it first (see [Resource locks](../../modules/wordpress-site/README.md#resource-locks)). Setting the flag back to `true` creates a new slot with a new managed identity, so `staging_slot_principal_id` changes and any access you granted the old identity outside the module must be granted again.

The new `staging_slot_enabled` output is known at plan time. `staging_slot_hostname` and `staging_slot_principal_id` are `null` when it is `false`; do not drive a `count` from either of them.

## v4.3.0: the scheduled App Service backup

**New, optional: `app_service_backup_enabled` (default `false`) and `app_service_backup`**, with `backup_*` inputs on the app-service module and `backup_container_lifecycle` on the storage module. Unset, nothing changes. See [Backup & Recovery](../../modules/wordpress-site/README.md#backup--recovery).

Turning it on schedules a custom App Service backup of the **production app only** (the staging slot is never backed up) to a private container in the site's storage account. Each backup is a complete copy of the app's `/home` and its configuration, capped at **10 GB**; the database is not included, and MySQL point-in-time restore covers it. What to know before you opt in:

- **The container is yours to declare.** `app_service_backup.container_name` (default `wp-backups`) must be a private entry of `storage.additional_containers`, for example `storage = { additional_containers = { "wp-backups" = {} } }`; the plan fails otherwise. The module does not create the container, so turning the backup off later leaves the backups in place.
- **Plan shape.** On an existing site the first plan adds the `backup` block and `virtual_network_backup_restore_enabled` to the web app, and `virtual_network_backup_restore_enabled` to the slot when one exists, as in-place updates. Nothing is replaced. It also creates `time_rotating.backup_sas[0]`, `time_offset.backup_sas_start[0]` and `time_offset.backup_sas_expiry[0]`, and adds a `backup-version-cleanup` rule to the storage account's lifecycle management policy while retention is finite.
- **The SAS is module-generated and rotates.** The module signs a container SAS from the account key at plan time; no SAS crosses the module boundary and none is an output. It is valid for `sas_validity_days` (default 365) and re-issued by the first plan after `sas_rotation_days` (default 180); validity must be at least twice the rotation interval, or the plan fails. A rotation shows as a replacement of the three `time` resources and an in-place update of the web app's backup block. Read `app_service_backup_sas_rotation_rfc3339` from a scheduled plan-only run: the backup fails after `app_service_backup_sas_expiry_rfc3339` if no plan has been applied since the rotation date. Rotating the account key invalidates the SAS until the next apply re-issues it. See [The SAS: source, rotation and trade-off](../../modules/wordpress-site/README.md#the-sas-source-rotation-and-trade-off).
- **The first plan defers the SAS read once.** The plan that turns the backup on creates the rotation timestamp, so the SAS data source is read at apply time and the app's `storage_account_url` is `(known after apply)` that once. It is noise, not damage: the URL feeds no identity or ForceNew argument, so the app plans an in-place update. Later plans read the SAS at plan time, unless the storage account is being created or replaced or the SAS is rotating. A `depends_on` on your own call to the module defers the read on every plan: do not add one.
- **Limits checked at plan.** App Service allows one custom backup every 2 hours at most, so `frequency_unit = "Hour"` needs `frequency_interval >= 2`. `retention_period_days` is 0 to 30 (0 keeps backups indefinitely); App Service accepts nothing longer. Both are rejected at plan rather than at apply.
- **The lifecycle rule for backup versions.** While `retention_period_days` is finite, the storage module adds a second lifecycle rule, scoped to the backup container, that deletes previous versions and snapshots after the same number of days: with blob versioning on (the default), a backup App Service deletes at the end of its retention would otherwise survive as a previous version that nothing reclaims. Base blobs are left to App Service, the uploads rule is unchanged, and the policy exists while this rule is wanted even with `storage.lifecycle_policy_enabled = false`. See the storage module's [Backup container lifecycle](../../modules/storage/README.md#backup-container-lifecycle).
- **The firewall can stay `Deny`.** The backup travels over the VNet integration and the App Service subnet is allow-listed, so `storage_network_rules_default_action = "Deny"` works. A restore into a **new** app needs its own route to the account; see [Restoring](../../modules/wordpress-site/README.md#restoring).

## v4.3.0: the `storage-key` secret opt-out

**New, optional: `storage_key_secret_enabled`**, default `true`. Unset, nothing changes: the module keeps writing the storage account's primary access key to the site's Key Vault as the `storage-key` secret. See [Retiring the `storage-key` secret](../../README.md#retiring-the-storage-key-secret).

The secret's only reader in the module is the `MICROSOFT_AZURE_ACCOUNT_KEY` app setting, which exists so an operator can install a Blob offload plugin; the module installs none and media stays on the app's `/home` storage by default. If you run no such plugin, turn both switches off:

```hcl
  app_service_storage_plugin_app_settings_enabled = false
  storage_key_secret_enabled                      = false
```

The order matters. `storage_key_secret_enabled = false` while `app_service_storage_plugin_app_settings_enabled` is still `true` **fails at plan**, because that setting is a Key Vault reference to the secret: turn the app settings off first (an in-place update of the app and the slot, which removes the account key from the app's environment), or set both in one change. On an existing site, `false` **destroys** the `storage-key` secret (a soft-delete in the vault; lift a CanNotDelete lock first) and changes nothing else. The account's shared-key access setting is unchanged, and the scheduled backup's SAS is derived from the account key directly, not from this secret, so the backup keeps working.

This release corrects the media wording in the module READMEs and variable descriptions along the same lines: media stays on `/home` unless you install a Blob offload plugin yourself, and `Deny` on the storage firewall is viable whenever no browser reads the blob endpoint. See [Media](../architecture.md#media).

## v4.3.0: passwordless database access (managed identity)

**New, optional: `mysql_entra_server_identity`, `mysql_entra_admin`, `mysql_entra_app_identity`, `mysql_entra_app_database_user`, `mysql_entra_admin_wait_seconds`, the four stage flags `mysql_entra_stage_identity_enabled`, `mysql_entra_stage_app_switch_enabled`, `mysql_entra_stage_drop_password_enabled` and `mysql_entra_stage_aad_only_enabled`, and the hardening input `mysql_require_secure_transport`; new output `mysql_entra_stage`.** Everything is off by default: a plan that sets none of them is unchanged apart from the output, which reports `0`. See [Passwordless database access (managed identity)](../../modules/wordpress-site/README.md#passwordless-database-access-managed-identity) for the two layouts, the rehearsal findings and the full stage table; this section is the upgrade checklist.

The module creates no identity, grants no Microsoft Graph permission and creates no MySQL user: you create the user-assigned identities and any non-administrator MySQL user yourself, and the deploying principal needs Managed Identity Operator on both identities.

**One stage per apply.** The four flags each require the one before it; turning on a later flag alone fails at plan. Apply, check the site, then turn on the next one. Enabling several at once is ordered safely (the app switch happens before Entra-only authentication) but gives you no point to verify between them.

| Stage | Flag | What the apply changes |
| --- | --- | --- |
| 1 | `mysql_entra_stage_identity_enabled` | Attaches the server identity to the MySQL server, creates the Entra administrator (after `mysql_entra_admin_wait_seconds`, default 30, because a freshly attached identity can still be propagating) and attaches the app identity to the production app, which becomes `SystemAssigned, UserAssigned`. No app setting changes; the app keeps using its password. |
| 2 | `mysql_entra_stage_app_switch_enabled` | Sets `ENABLE_MYSQL_MANAGED_IDENTITY=true`, `ENTRA_CLIENT_ID` and `DATABASE_USERNAME` on the production app. The container restarts. **Check the `wp-config.php` prerequisite first.** |
| 3 | `mysql_entra_stage_drop_password_enabled` | Removes `DATABASE_PASSWORD` from the production app. The `db-password` secret is still written, because the way back needs it. |
| 4 | `mysql_entra_stage_aad_only_enabled` | Sets the server parameter `aad_auth_only = ON`, ordered after the app update, so password logins stop for everyone, the `wpadmin` administrator included. |

None of the stages replaces the MySQL server or the web app: the server's identity block, the administrator and the parameter are updated in place by azurerm 5.x, and so is the web app's identity block. Turning a flag off reverses that stage.

- **The `wp-config.php` prerequisite before stage 2.** Stage 2 only flips app settings. The image reads `ENABLE_MYSQL_MANAGED_IDENTITY` from a block its first install wrote into the site's persistent `wp-config.php`. A site installed by an older image has no such block, and with the settings flipped it **would lose database access**. Before turning stage 2 on, open an SSH session to the production app and run `grep -c ENABLE_MYSQL_MANAGED_IDENTITY /home/site/wwwroot/wp-config.php`. A non-zero count means go ahead. A `0` means you must run the image's own managed-identity setup procedure yourself, inside the container and outside this module, as the composition README describes; take a backup first.
- **Which ID is the administrator's `object_id`.** The module passes `mysql_entra_admin.object_id` to the provider exactly as given. The azurerm documentation says that for a managed identity it should be the identity's **client ID**; the design's rehearsal on a real server set the administrator by the identity's **principal (object) ID** and that worked. These disagree, so confirm on the first stage-1 apply on a non-production server and use the value your rehearsal proved.
- **Settings the stages own.** From stage 2, `app_service.extra_app_settings` and `extra_secret_app_settings` may not name `ENABLE_MYSQL_MANAGED_IDENTITY`, `ENTRA_CLIENT_ID` or `DATABASE_USERNAME`, may not set `CACHE_MYSQL_ACCESS_TOKEN` to `true` or `DB_SSL_CONNECTION` to `false`, and from stage 3 may not name `DATABASE_PASSWORD`; each fails at plan. A consumer that already sets one of these must remove it before that stage.
- **The staging slot and stage 4.** The slot is never given the app identity and keeps its password settings at every stage (with a slot, the four database settings become sticky, so a swap leaves each side's login where it is). `aad_auth_only` would lock the slot out, so stage 4 **fails at plan while a slot exists**: set `app_service.staging_slot_enabled = false` first, which destroys the slot as the staging-slot section above describes, then turn stage 4 on.
- **Rolling back.** Reverse order, one apply per step, and the password returns **before** the app switches back: stage 4 off (deletes the parameter's configuration resource, which resets `aad_auth_only` to `OFF`), then stage 3 off (`DATABASE_PASSWORD` returns from the Key Vault secret that was never removed), then stage 2 off (the app is back on `wpadmin` and the password), then stage 1 off (removes the administrator, the server identity and the app identity attachment). The flags enforce this order: switching a lower stage off while a higher one is on fails at plan. MySQL users you created stay; drop them yourself.
- **`mysql_require_secure_transport`** is a hardening input, not a stage. The default `false` keeps the `OFF` every earlier release set; `true` refuses any client that does not use TLS, at once, so check the app and any other client first.
