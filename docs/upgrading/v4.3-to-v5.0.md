# 4.3 to 5.0

This page covers **v5.0.0** (not yet cut when this page was written; it is the major release the release tool proposes for the changes below). Pin `?ref=v5.0.0`. The release removes two inputs that nothing read: the Cloudflare account ID, and the deprecated `plan_density_limit` of `modules/wordpress-site`. The release changes no resource. A consumer on v4.3.5 plans **no changes** once the configuration is edited as the table below says.

If you are on a release before v4.3.5, read the rows for v4.3.3, v4.3.4 and v4.3.5 in the [upgrade guide](README.md) first. v4.3.4 and v4.3.5 can change plans, and taking v5.0.0 takes them too.

## Who is affected, and what to do

| Your configuration | What happens when you move the pin | What to do |
| --- | --- | --- |
| You call `modules/cloudflare` yourself and pass `cloudflare_account_id` | Terraform stops with `Unsupported argument` before it plans anything | Delete the argument from the `module` block |
| You call `modules/wordpress-site` and set `plan_density_limit` | Terraform stops with `Unsupported argument` before it plans anything | Delete the argument from the `module` block: see [Callers that set `plan_density_limit`](#callers-that-set-plan_density_limit) |
| You call `modules/wordpress-site` and set `account_id` inside the `cloudflare` object | Nothing fails and no warning is printed. Terraform drops the attribute when it converts your object to the variable's type | Nothing is required. Delete the line when you next edit the block |
| You call `modules/wordpress-site` and set neither `plan_density_limit` nor `cloudflare.account_id` | Nothing | Nothing |
| You copied `examples/basic-site` or `examples/multi-site` | Your copy still declares its own `cloudflare_account_id` variable and passes it as `cloudflare.account_id`, which is the third row. Neither example ever set `plan_density_limit` | Optional clean-up: see [Removing your own variable](#removing-your-own-variable) |

No output changed, and no provider requirement changed.

## What was removed, and why

- `modules/cloudflare`: the required, sensitive input `cloudflare_account_id`.
- `modules/wordpress-site`: the `account_id` attribute of the `cloudflare` object, which did nothing except feed that input.
- `modules/wordpress-site`: the optional input `plan_density_limit` (a number, default `10`), with its validation, which accepted 1 to 20.

No resource, data source, local value or output in the Cloudflare module referenced the variable, so the value never reached Cloudflare. The module finds the zone by `domain` and the provider signs in with the API token you configure in your root, so neither needs the account ID. A static check reported the variable as declared but unused ([#168](https://github.com/agenticcodingops/azure-wordpress/issues/168)). Removing an input breaks any caller that still passes it, which is why this is a major release.

Nothing in the composition module referenced `plan_density_limit` either, so it never limited the number of sites on an App Service plan. v4.1.0 deprecated it and kept it, so that configurations that set it still planned ([4.0 to 4.1](v4.0-to-v4.1.md#upgrading-to-v410)). The same static check reported it as declared but unused, and the maintainer decided to remove it in the same major release as the account ID, so that callers edit once ([#177](https://github.com/agenticcodingops/azure-wordpress/issues/177)).

## What this release keeps

One removal that earlier text tied to "the next major release" is **not** part of v5.0.0. That text now says "a later major release".

**The `azapi` provider requirement of `modules/wordpress-site` stays.** No resource has used the provider since v4.3.5. The requirement remains so that a state written by an earlier release plans the removal of the old Front Door restriction patch without a manual step, as [Front Door origin access restrictions](front-door-origin-restrictions.md) describes, and a caller can move to v5.0.0 straight from such a release. `terraform init` still downloads the provider.

## Expected plan

**No resource changes against v4.3.5.** Neither removed value fed a resource argument, so there is nothing for a plan to show.

This was measured for the Cloudflare account ID, offline, on Terraform 1.9.8 and 1.17.1: the composition module was planned with every provider mocked, `cdn_provider = "cloudflare"`, from v4.3.5 and from the tree with the input removed, and the two verbose plans were compared. They were identical in both fixtures:

- a caller that never set the account ID (40 resources planned on each side, 5 of them Cloudflare);
- a caller that still sets `account_id`, with every Cloudflare feature flag on (58 resources planned on each side, 23 of them Cloudflare).

It was measured again for `plan_density_limit`, in the same way and on the same two Terraform versions, with `cdn_provider = "direct"`, from the tree before and after that removal. The fixture never sets the input; a caller that does set it has no plan to compare, because Terraform rejects the configuration first. The two verbose plans were identical for each of three callers:

- nonprod on an S1 plan (34 resources planned on each side);
- nonprod on a B1 plan (32 on each side);
- production on an S1 plan (34 on each side).

Limits of both measurements: these are greenfield create plans against mocked providers, so they prove identical planned arguments, not provider-side diffing against real state. A mocked provider cannot return a zone from the zone lookup, so in the Cloudflare measurement both sides carried the same one-line fallback for the zone ID. A plan against real state needs deployment credentials: read your own nonprod plan before you apply, as [Upgrade the module](../operations/upgrade-the-module.md) describes.

## Direct callers of the Cloudflare module

A `module` block that still passes the input fails as soon as Terraform loads the configuration:

```text
Error: Unsupported argument

  on main.tf line 14, in module "cloudflare":
  14:   cloudflare_account_id = "stale-value"

An argument named "cloudflare_account_id" is not expected here.
```

Which command prints it depends on the Terraform version. Measured on both versions in the order an upgrade runs: a caller that passes the argument is initialised and valid at v4.3.5, then its module source is moved to this release:

| Terraform | `terraform init` after the move | `terraform validate` after that init |
| --- | --- | --- |
| 1.9.8 | succeeds | fails with the error above |
| 1.17.1 | fails with the error above | fails with `Module source has changed`, because the failed init installed nothing |

So on 1.17.1 the error above appears at `terraform init`, and `validate` asks for an init until one succeeds. In a directory that was never initialised, `validate` on 1.17.1 fails with `Module not installed` instead. On both versions, `validate` run after the move and before any init also fails with `Module source has changed`. On 1.17.1, `validate` prints the error above only when the new module is already installed, which takes an init without the argument.

The same caller with the argument deleted initialises and validates on both versions. `terraform plan` was not run for this page; like `validate`, it reads the installed modules and the configuration before it contacts any provider.

Delete the argument:

```hcl
module "cloudflare" {
  source = "github.com/agenticcodingops/azure-wordpress//modules/cloudflare?ref=v5.0.0"

  # cloudflare_account_id = var.cloudflare_account_id   # delete this line
  domain       = "example.com"
  cdn_provider = "cloudflare"
  # ...
}
```

Change the pin and delete the argument in the same commit. Through v4.3.5 the input is required, so the two cannot be done in either order on their own: v4.3.5 without the argument fails with `Missing required argument`, and v5.0.0 with it fails as shown above.

## Callers of the composition module

A `cloudflare` object that still carries `account_id` keeps working:

```hcl
  cloudflare = {
    enabled    = true
    account_id = var.cloudflare_account_id # ignored from v5.0.0; safe to delete
    domain     = "example.com"
    subdomain  = "blog"
  }
```

Terraform converts the object you pass to the variable's declared object type, and an attribute the type does not declare is dropped in that conversion. Measured on Terraform 1.9.8 and 1.17.1:

- a root module that calls `modules/wordpress-site` with the block above passes `terraform validate` with no error and no warning;
- `terraform console` on the module shows `var.cloudflare` without an `account_id` key when the value is supplied with one;
- a plan of that root with every provider mocked succeeds, plans the Cloudflare resources, and contains the stale value nowhere.

So no edit is required to take v5.0.0. Delete the line when you next touch the block, so the configuration does not suggest the value is used.

## Callers that set `plan_density_limit`

A `module` block for `modules/wordpress-site` that still sets the input fails as soon as Terraform loads the configuration:

```text
Error: Unsupported argument

  on main.tf line 25, in module "site":
  25:   plan_density_limit = 5

An argument named "plan_density_limit" is not expected here.
```

Which command prints it depends on the Terraform version, in the same way as for the Cloudflare input. Measured on both versions in the order an upgrade runs: a caller that sets the argument is initialised and valid at v4.3.5, then its module source is moved to this release:

| Terraform | `terraform init` after the move | `terraform validate` after that init |
| --- | --- | --- |
| 1.9.8 | succeeds | fails with the error above |
| 1.17.1 | fails with the error above | fails with `Module source has changed`, because the failed init installed nothing |

The other cases were measured too, and match the Cloudflare input. On both versions, `validate` run after the move and before any init fails with `Module source has changed`. In a directory that was never initialised, 1.9.8 initialises and `validate` prints the error above, while on 1.17.1 `init` prints it and `validate` fails with `Module not installed`. On 1.17.1, `validate` prints the error above only when the new module is already installed, which takes an init without the argument; on 1.9.8 any init installs it.

The same caller with the argument deleted initialises and validates on both versions. `terraform plan` was not run for this caller.

Delete the argument:

```hcl
module "site" {
  source = "github.com/agenticcodingops/azure-wordpress//modules/wordpress-site?ref=v5.0.0"

  # plan_density_limit = 10   # delete this line
  project_name = "example"
  # ...
}
```

Unlike the Cloudflare input, this one was optional, so you can delete the argument first, while the pin is still at v4.3.5, and move the pin later; or do both in one commit. Only moving the pin first fails. Deleting it changes no plan on either release, because no value of it ever reached a resource.

If your root declares a variable only to feed this argument, delete that variable too, and then remove the value wherever you supply it. Terraform treats a value for an undeclared root variable differently by source, as the table under [Removing your own variable](#removing-your-own-variable) shows. The same was measured, on 1.9.8 and 1.17.1 with `terraform console`, for a root that no longer declares `plan_density_limit`: a line left in `terraform.tfvars` prints the warning `Value for undeclared variable` and Terraform continues; `-var plan_density_limit=...` stops with the error `Value for undeclared variable`; the `TF_VAR_plan_density_limit` environment variable is ignored silently.

## Removing your own variable

The examples no longer declare `cloudflare_account_id`. If your root declares a variable that existed only to feed `cloudflare.account_id`, you can delete it together with the `account_id` line. Then remove the value wherever you supply it, because Terraform treats a value for an undeclared root variable differently by source (measured on 1.9.8 and 1.17.1 with `terraform console`):

| Where the value is still supplied | What Terraform does |
| --- | --- |
| A line in `terraform.tfvars` or another variables file | Prints the warning `Value for undeclared variable` and continues |
| `-var cloudflare_account_id=...` on the command line | Stops with the error `Value for undeclared variable` |
| The `TF_VAR_cloudflare_account_id` environment variable | Ignores it silently |

A pipeline secret that existed only to supply the account ID can be retired once nothing passes it. Your Cloudflare API token is unaffected: the module reads the zone and manages the same resources as before.

## Rollback

Set the previous `?ref=`. A direct caller of `modules/cloudflare` must restore the `cloudflare_account_id` argument in the same change, because every release through v4.3.5 requires it; any string works, since the value was never used. A caller of the composition module needs no edit to go back: every release through v4.3.5 declares `plan_density_limit` with a default, so a configuration without the argument is valid there, and you can leave it deleted. No state changes in either direction.
